# ITLS 渐进优化

读根 `AGENTS.md`。用户要求的优化包含三条线：代码维护、业务操作、运行性能。先执行 `python scripts/quality/repo_inventory.py`，再依据本次问题采集指标；文件大不等于无用，Maven 多模块不等于微服务，不要按目录数量盲目合并。

## 选择改动

- 维护：找同职责重复实现及调用方，优先共用已有 Gi/Base 组件、文件导出、状态处理和 PSI 库存接口。公共抽象至少有真实调用需求；迁移 compat 时按一个业务闭环收敛。
- 操作：选用户任务，记录角色、入口、页面跳转、重复录入和提交次数。对报价转工单、报修派单、维修结算减少重复填写并保留权限与审计。以实际截图/操作观察为证据；没有交互证据时只能提出待验证设计，不能称 UX 已优化。
- 性能：分别测安装、增量构建、冷启动、首页、业务接口 P50/P95 和资源占用。记录机器、缓存、数据量与样本数；优先请求合并、按需加载、查询分页、依赖去重和关闭无用开发插件加载。

## 执行与验收

先说明问题、证据、目标、改动边界；选择一批可逆且独立验证的改动，保持现有业务。删除功能、菜单、历史数据或模块前核查调用、路由、权限、SQL、部署、导出、H5 和跨域依赖；未经业务取舍不要以“精简”为由删除仍可达能力。

每批记录前后指标和回归结果。构建时间、产物体积、内存、响应时间是不同指标，不能互相替代；无同环境对照就明确“未量化”。涉及业务的改动按业务测试 Skill 运行对应闭环和反例。

把问题清单、已实施项、剩余项和收益证据写入 `Docs/releases/maintenance.md`，不要另造优化报告目录。先做高频主链，再决定是否合并低频管理页；避免一次重写整个底座。

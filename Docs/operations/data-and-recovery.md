# 数据与密钥生命周期

## 持久化边界

| 内容 | 角色 | 管理边界 |
|---|---|---|
| MySQL | 业务记录、状态与关联 | 独立数据目录或命名卷 |
| Redis | 会话、缓存及相关运行状态 | 按部署配置持久化，恢复策略与业务库分开 |
| 附件与签署材料 | 文件正文及签署输出 | 与数据库文件记录配套保存 |
| 国密及运行密钥 | 加解密与相关安全能力 | 独立持久化，受限访问 |
| 真实环境配置 | 连接信息、凭据和运行参数 | 不进入源码仓库 |

根生产Compose使用宿主绑定目录；已有本机覆盖复用MySQL/Redis外部卷。后端通过 `/app/data` 保存运行文件，通过 `/app/logs` 保存日志。实际位置由部署配置与挂载决定。

## 备份关系

数据库、附件、签署材料、密钥和必要环境配置形成一套恢复单元。仅保存SQL不能恢复文件正文，丢失原密钥可能导致旧数据无法解密。备份版本需要对应应用版本、数据库结构和文件存储状态。

scripts/backup.sh按其生产目录布局工作；命名卷布局需采用相应数据库与卷备份方式。私有备份存放在源码目录之外，访问权限和保留周期由运维策略管理。

## 恢复顺序

恢复先准备独立的目标目录、数据库和运行配置，再加载匹配的数据库、文件与密钥，核对结构、关联关系和解密能力，最后按切换计划接入业务入口。恢复操作不直接覆盖仍在使用的数据集。

重建镜像和容器不要求清空业务存储。数据库升级属于结构演进，源码更新属于应用演进，两者的版本与回退边界需要分别管理。删除数据卷、绑定目录或重新初始化不能作为一般启动问题的处理方式。
